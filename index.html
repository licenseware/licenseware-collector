Product Overview

What is LICENSEWARE Collector?
A free lightweight agent that collects system and software inventory data from your servers and securely transmits it to the LICENSEWARE ™ platform for software license compliance analysis.

Operating System Compatibility

Linux

  • x86_64 and arm64 (64-bit)
  • systemd required
  • RHEL, Ubuntu, Debian, etc.

Windows

  • x86_64 (64-bit) only
  • Windows 10+ (Desktop)
  • Windows Server 2016+

macOS

  • Intel & Apple Silicon
  • macOS 12+
  • launchd service
⚠️ Older Windows versions
Windows 7, Windows 8.1, Windows Server 2012 R2 and earlier are not supported. The agent requires Windows 10 or Windows Server 2016 or later.

Network Requirements

  • api.licenseware.ioHTTPS 443
    Primary API for data ingestion, enrolment and configuration. Regional tenants use api.us.licenseware.io or api.au.licenseware.io instead — the agent follows the issuer in its enrolment token.
  • pushlogs.licenseware.ioHTTPS 443
    Agent log shipping, enabled by default (LOG_SHIP_ENABLED). Regional tenants use pushlogs.us.licenseware.io or pushlogs.au.licenseware.io.
  • cdn.licenseware-collector.comHTTPS 443
    Installer downloads, and osquery updates (manifest and binaries), which the agent checks continuously. From 0.17.0 agent updates come from here too. Required continuously, not just at install time.
  • api.github.comHTTPS 443
    Agent self-update on 0.16.0 and earlier: Windows and Linux agents check for a new release every 24 hours (macOS agents on those versions never self-update). From 0.17.0 agents update from cdn.licenseware-collector.com and no longer need this host.
  • release-assets.githubusercontent.comHTTPS 443
    Self-update and osquery fallback downloads on 0.16.0 and earlier — GitHub redirects here. Also allow the legacy host objects.githubusercontent.com. Not needed from 0.17.0.
  • github.comHTTPS 443
    osquery fallback download on 0.16.0 and earlier. Not used by an MSI or package install, which bundle osquery already. Not needed from 0.17.0.
⚠️ Firewall Configuration
Ensure outbound HTTPS (port 443) is allowed to the domains listed above. No inbound ports required.

System Requirements

    64-bit only (32-bit not supported)
  • Disk Space
    ~100 MB for binaries and temp files
  • Memory
    Minimal (~50 MB during operation)

Single machine

From 0.17.0

Install on one machine by hand. You need an enrolment token and administrator rights. Each install enrols the machine and finishes only once Licenseware has registered it, usually within seconds and at most 3 minutes.

Windows (Administrator Command Prompt)

msiexec /i LicensewareCollector.msi TOKEN=<enrolment-token>

Download LicensewareCollector.msi from Downloads first. If the machine cannot register (a rejected token, no network), the installer removes itself again and exits 1603; the reason is in %ProgramData%\Licenseware\setup.log. Double-clicking the .msi without a token is refused: pass the token on the command line.

macOS (Terminal)

curl -fsSLO https://cdn.licenseware-collector.com/d/latest/LicensewareCollector.pkg
sudo mkdir -p /usr/local/etc
sudo install -m 0600 /dev/null /usr/local/etc/licenseware-collector
echo 'TOKEN=<enrolment-token>' | sudo tee /usr/local/etc/licenseware-collector >/dev/null
sudo installer -pkg LicensewareCollector.pkg -target /

The package reads the token from that root-only file, enrols the Mac and waits for it to register. If it does not register, installer reports that the installation failed, and the reason is in /var/log/install.log.

Linux

curl -fsSL https://cdn.licenseware-collector.com/install.sh | sudo TOKEN=<enrolment-token> sh

The script picks the .deb or .rpm for this machine, checks it against the release's SHA256SUMS, installs it and waits for the machine to register. If it does not register, the script removes the package again and exits 1. Its options (--token-file, --proxy, --version) are in Ansible / Linux fleets.

To check a machine, run status: it exits 0 once the machine is registered (Day-2 operations). Behind a proxy or TLS inspection, see Settings: the MSI takes PROXY= and CA_CERT= beside TOKEN=, the Mac file takes them as extra lines, and install.sh takes --proxy URL.

On 0.16.0 and earlier

Windows: the same msiexec line enrols the machine, but exit code 0 does not prove it is registered; check with status.

To stage the files now and enroll later, omit TOKEN. No service is created until you run: set TOKEN=<enrollment-token> then "%ProgramFiles%\Licenseware\LicensewareCollector.exe" register.

macOS and Linux: install the package, then enrol the machine.

sudo installer -pkg LicensewareCollector.pkg -target /
sudo TOKEN=<enrolment-token> /usr/local/licenseware-collector/seed/licenseware-collector register
sudo apt install ./licenseware-collector_amd64.deb
# RHEL / Fedora / SUSE: sudo dnf install ./licenseware-collector_amd64.rpm
sudo TOKEN=<enrolment-token> licenseware-collector register

Intune / SCCM (Windows)

From 0.17.0

Deploy LicensewareCollector.msi (Downloads) as a Win32 app in Intune or an application in SCCM. It runs as SYSTEM with no user interaction. When msiexec returns 0 on a new device, the device is enrolled and registered and its service is running.

Deployment of the Collector through automated tools such as Intune or SCCM constitutes acceptance of the Collector Licence Agreement by the deploying organisation.

Install command

msiexec /i LicensewareCollector.msi TOKEN=<enrolment-token> /qn /norestart

A TOKEN= value is visible wherever the command line is logged (MDM logs, process-creation auditing). To keep it off every command line, put the token in a file that SYSTEM can read (ASCII, the token on the first line) and pass its absolute path instead. The installer never deletes that file.

msiexec /i LicensewareCollector.msi TOKENFILE=C:\path\to\token.txt /qn /norestart

Proxy, CA certificate, update and log settings are MSI properties with the same names: PROXY, NO_PROXY, CA_CERT, AUTOUPDATE and LOG_LEVEL (Settings). Requirements: 64-bit Windows 10, or Windows Server 2016 and later (OS Compatibility).

Exit codes

Keep Intune's default return codes (0 and 1707 success, 3010 soft reboot, 1641 hard reboot, 1618 retry) and add none: the MSI returns only standard Windows Installer codes.

CodeMeaning
0Installed. On a new device also registered: Registered = 1 and the service running when msiexec returns
3010Success, reboot pending (files in use; the package itself schedules no reboot)
1603Refused, or failed and rolled back (below)
1618Another installation is already in progress
1619 / 1620Package path unreachable, or not a valid installer package

What 1603 means

  • A fresh install without TOKEN or TOKENFILE, or with both, is refused before anything is written. The reason is in the msiexec /l*v log.
  • A fresh install whose token is rejected, that cannot reach Licenseware, or that is not registered within 3 minutes rolls back completely. It leaves only %ProgramData%\Licenseware\setup.log, which says why: register exit 10 means not acknowledged in time, 11 the service stopped, 12 the token was rejected.
  • An upgrade or a repair fails only when no service is left at the end. Windows Installer then restores the previous version.

An offline device therefore fails with 1603 instead of installing an agent that never reports, and Intune retries it. During the wait of up to 3 minutes, other installs on the device get 1618.

Detecting a registered agent

From Collector 0.16.0 the agent records whether the Licenseware backend has acknowledged it. On Windows that state is mirrored into the registry, so Intune and SCCM can use a built-in registry rule — no script. Do not use a file-version or product-code rule: both report success even when enrolment did not complete.

Setting Value
Rule type Registry
Key path HKEY_LOCAL_MACHINE\SOFTWARE\Licenseware\Collector
Value name Registered
Detection method Integer comparison, Equals, 1
Associated with a 32-bit app on 64-bit clients No

SCCM uses the same key and value for an application detection method and for a compliance configuration item. The key also carries Status, AgentId, DeviceUuid, Version, RegisteredAt and LastContactAt as strings for hardware inventory.

On every platform the same information is in a world-readable file with no secrets: registration.json in the agent's state directory (see Installation Paths). Its status is enrolled until the backend acknowledges the agent, then registered. The status command reads it and exits 0 only when registered (2 enrolled only, 3 no state file, 4 no service); status --json prints the file. 

licenseware-collector status --json
jq -e '.status == "registered"' /var/lib/licenseware-collector/registration.json
⚠️ Switch detection rules after the fleet is on 0.16.0
Devices installed before 0.16.0 gain the key and the file only after they self-update and complete one check-in, about a minute after the restart. A required assignment whose detection rule already expects the key would treat those devices as not installed and re-run the installer on them. Keep the script below until the console shows the fleet on 0.16.0 or later.

Agents older than 0.16.0: use this PowerShell detection script. The TOKEN= line is written only by a completed enrolment and the Windows service is created only by register; together they mean the agent has enrolled, though not that the backend has acknowledged it. 

$svc = Get-Service licenseware-collector -ErrorAction SilentlyContinue
$env = "$env:ProgramData\Licenseware\collector.env"
if ($svc -and (Test-Path $env) -and (Select-String -Path $env -Pattern '^TOKEN=..*' -Quiet)) {
    Write-Output "Installed"
    exit 0
}
exit 1

Upgrades

Assign the newer MSI with the same command (Intune supersedence, or a new SCCM deployment type). It never downgrades: an older MSI keeps a newer, self-updated agent and osquery. Run without a token, it repairs and leaves a running service alone. Run with TOKEN, it re-enrols the device: a new credential for the same agent, or a move to the token's project. Devices enrolled without the MSI are upgraded by it without a token.

Agents also update themselves from cdn.licenseware-collector.com. To leave upgrades to your MDM only, install with AUTOUPDATE=0.

Uninstall

msiexec /x LicensewareCollector.msi /qn /norestart

Intune and SCCM run it from the app's content. On the device itself, LicensewareCollector.exe uninstall does the same (Day-2 operations); see also the Uninstall Guide.

On 0.16.0 and earlier

Only TOKEN is an MSI property; TOKENFILE, PROXY, NO_PROXY, CA_CERT, AUTOUPDATE, LOG_LEVEL and ENROLL_ON_START need 0.17.0. Exit code 0 does not prove registration: an install without TOKEN stages the files and creates no service, and a registration that fails after enrolment still exits 0. A rejected token fails with 1603, and a TOKEN given to an enrolled device is ignored. Rely on the detection rule above.

Jamf, Intune for Mac, Kandji (macOS)

From 0.17.0

Works with any MDM that deploys configuration profiles and packages. The three steps can happen in any order: a package that arrives before the profile fails, and succeeds when the MDM retries it.

  1. Push the configuration profile

    Download it from the install instructions the Licenseware app shows when you create an API key (the key is filled in), or take the template io.licenseware.collector.mobileconfig and replace REPLACE_WITH_ENROLMENT_TOKEN with your token. Set PROXY, NO_PROXY or CA_CERT only if your network needs them (Settings). Deploy it as a device-level profile.

    The settings live in the managed preferences domain io.licenseware.collector. The profile's second payload approves the collector's background service (Team ID 8MD7XA4CF3), so macOS 13 and later show no "Background Items Added" notice. A changed profile reaches a registered Mac at its next package run.

  2. Deploy the package

    Deploy LicensewareCollector.pkg to the same Macs. It reads the token from the profile, enrols the Mac and waits up to 3 minutes for it to register. Otherwise the install fails and your MDM retries it at the next check-in. The reason is in /var/log/install.log: 20 no token yet, 21 token rejected (expired or revoked), 22 enrolment failed (network, proxy, TLS), 23 not registered within 3 minutes.

    The package is universal (Apple silicon and Intel) and needs no Rosetta. An older package never downgrades a newer agent. Agents update themselves from the CDN; set AUTOUPDATE to false in the profile to leave upgrades to your MDM.

  3. Report registration with an extension attribute

    Add status-attribute.sh as a Jamf extension attribute (string; it prints <result>registered</result>), or as an Intune or Kandji custom attribute run with --plain. Its values are registered, enrolled, absent, no-service, not-installed and error(<code>).

    Build a smart group of the Macs whose value is not registered and scope the profile to it. The token then leaves each Mac once it is registered: local users may be able to read managed preferences, and the token can enrol more devices into your account (it gives no access to data).

Privacy rules (PPPC / TCC)

From 0.17.0 the agent is signed with the identifier io.licenseware.collector (osquery: io.licenseware.collector.osqueryi). PPPC profiles or TCC grants that name licenseware-collector or LicensewareCollector stop matching new binaries: add the new identifier and keep the old ones until every Mac has updated. Rules by Team ID (8MD7XA4CF3) are unaffected.

On 0.16.0 and earlier

The package only installs files, and agents on 0.16.0 and earlier never update themselves. Push the package, then run this on each Mac as root, for example in a Jamf policy script. The profile and its settings need 0.17.0; status-attribute.sh also works with 0.16.0 agents.

sudo TOKEN=<enrolment-token> /usr/local/licenseware-collector/seed/licenseware-collector register

Ansible / Linux fleets

From 0.17.0

For Ansible, Puppet, Salt or any tool that runs commands as root. Each step is also what you would type by hand.

One task: install.sh

- name: Install the Licenseware Collector
  become: true
  ansible.builtin.shell: set -o pipefail && curl -fsSL https://cdn.licenseware-collector.com/install.sh | sh
  args:
    executable: /bin/bash
    creates: /var/lib/licenseware-collector/registration.json
  environment:
    TOKEN: "{{ licenseware_token }}"
  no_log: true

The script picks the package for the machine (apt, dnf, yum or zypper; amd64 or arm64), checks it against the release's SHA256SUMS, installs it and waits up to 3 minutes for the machine to register. If it does not register, the script removes the package again and exits 1, so the task fails and the next run retries. creates: stops the task from running again on an enrolled machine.

Options, after sh -s --: --token-file /root/lc-token reads the token from a root-only file (for sudo rules that refuse TOKEN=), --proxy URL downloads through a proxy and stores it for the agent, --version 0.17.0 pins a release, --no-enroll prepares a golden image, and --dry-run downloads and verifies without changing anything.

curl -fsSL https://cdn.licenseware-collector.com/install.sh | sudo sh -s -- --token-file /root/lc-token

Restricted sudo rules and proxies: pre-seed the env file

sudo passes TOKEN= only to rules that allow every command, and it drops HTTPS_PROXY. Write the settings to the env file as root first, then install the package with nothing else on the command line:

sudo install -m 0600 /dev/null /etc/default/licenseware-collector
printf 'TOKEN=%s\nPROXY=%s\n' '<enrolment-token>' 'http://proxy:3128' |
  sudo tee /etc/default/licenseware-collector >/dev/null
sudo apt install ./licenseware-collector_amd64.deb

In Ansible this is an ansible.builtin.copy task with mode: "0600" and force: false before the package task. Never overwrite the file afterwards: once the machine is enrolled, it holds the machine's own credential.

Package manager with TOKEN=

sudo TOKEN=<enrolment-token> apt install ./licenseware-collector_amd64.deb
sudo TOKEN=<enrolment-token> dnf install ./licenseware-collector_amd64.rpm

Packages for amd64 and arm64 are in Downloads. The package stores the token and starts the service, which enrols and registers the machine. It waits up to a minute to say whether registration finished; the service keeps retrying either way.

What the package checks first

  • A malformed or expired token, or one not issued by Licenseware, stops the install before any file is written: apt exits 100, dnf reports "Transaction failed", the package stays not installed and the next install works. The message gives the reason and where the token came from, never the token.
  • No token: the package installs, leaves the service stopped and prints the register command to enrol the machine later.
  • An enrolled machine keeps its own credential: a TOKEN given to an upgrade is ignored, so upgrades never re-enrol.

Checking the result

licenseware-collector status needs no root. Use exit code 0 as the success check, for example in an Ansible command task with changed_when: false:

CodeMeaning
0Registered
1The check itself failed
2Enrolled; registration not acknowledged yet (the service keeps retrying)
3No registration state: not enrolled, an enrolment still pending, or a golden image before its first start
4Service not installed
On 0.16.0 and earlier

Install the package, then enrol the machine: the package ignores TOKEN, and install.sh on the CDN needs 0.17.0. With Ansible, put creates: /var/lib/licenseware-collector/registration.json on the register task.

sudo apt install ./licenseware-collector_amd64.deb
# RHEL / Fedora / SUSE: sudo dnf install ./licenseware-collector_amd64.rpm
sudo TOKEN=<enrolment-token> licenseware-collector register

Golden images and VDI

From 0.17.0

For an image (VDI, Autopilot, a VM template) from which every machine enrols as itself. Install in image mode: the token is stored and the service is set to start at boot, but nothing is enrolled on the image.

Install in image mode

Windows

msiexec /i LicensewareCollector.msi TOKEN=<enrolment-token> ENROLL_ON_START=1 /qn /norestart

Linux

curl -fsSL https://cdn.licenseware-collector.com/install.sh | sudo TOKEN=<enrolment-token> sh -s -- --no-enroll
sudo TOKEN=<enrolment-token> ENROLL_ON_START=1 apt install ./licenseware-collector_amd64.deb

macOS

Set ENROLL_ON_START to true in the configuration profile, or add the line ENROLL_ON_START=1 to /usr/local/etc/licenseware-collector, before the package installs.

An agent that is already installed (any OS; on Windows set TOKEN=…, then LicensewareCollector.exe register --enroll-on-start):

sudo TOKEN=<enrolment-token> licenseware-collector register --enroll-on-start

Image mode checks the token offline (an enrolment token issued by Licenseware, not expired), stores it with ENROLL_ON_START=1, and installs the service set to start at boot without starting it. Nothing is enrolled and no machine identity is written; one left by an earlier install is removed. status exits 3 until the first start. A device credential or shared key is refused, because every clone would share it.

At the first start of each machine, the service enrols it with the stored token (retrying from 30 seconds up to hourly while Licenseware is unreachable), registers it, replaces the token with the machine's own credential and starts collecting. A revoked or expired token is retried hourly: put a new TOKEN in the env file, or run register with one.

Image hygiene

  • Never start the service on the image before you capture it. The first start stores that machine's identity, and every clone taken afterwards shares it.
  • Generalise the image the way the platform expects: sysprep on Windows, an empty /etc/machine-id on Linux.
  • Do not wait for registration while you build the image: in image mode the installers return at once and status exits 3.

Cloned machines

Each agent records a fingerprint of the machine it enrolled on (hardware serial and OS machine ID). On a machine cloned after the first start the fingerprint no longer matches: status prints CLONED IMAGE SUSPECTED, registration.json gets clone_suspected: true (on Windows, CloneSuspected = 1 under HKLM\SOFTWARE\Licenseware\Collector) and the log has reason=lc_clone_suspected. The identity is never changed automatically: uninstall the collector on the clone, then install and enrol it again.

On 0.16.0 and earlier

Image mode needs 0.17.0. On 0.16.0 and earlier, install without a token on the image (Windows: the MSI without TOKEN; Linux and macOS: the package only), then run register with the token on each machine after it is created.

Settings

One set of names works everywhere: as an MSI property, a key in the env file, an environment variable for register, apt, dnf or install.sh, a key in the macOS configuration profile, and a set key. A setting given at install time is stored in the machine's env file and wins over what the Licenseware control plane sends.

TOKENEnrolment token, replaced by the machine's own credential after enrolment. The MSI also takes TOKENFILE=<path>. To change it, run register.✓✓✓—
PROXYhttp://, https:// or socks5:// URL (a bare host:port means http), or direct for no proxy at all✓✓✓✓

Where the env file lives

Linux/etc/default/licenseware-collector
macOS/usr/local/etc/licenseware-collector
Windows%ProgramData%\Licenseware\collector.env

Readable by root or Administrators only. It holds only what was set on that machine (from 0.17.0 it starts with # licenseware-collector env format=2); everything else follows the control plane. The older names CA_CERT_PATH, SELF_UPDATE_ENABLED, HTTPS_PROXY and HTTP_PROXY are still read.

To change a setting later, run set, which validates it, stores it and restarts the service: sudo licenseware-collector set PROXY=http://proxy.corp:3128, and set PROXY= to remove it. After editing the file by hand, run restart (Day-2 operations).

Proxy

The agent picks its route in this order:

  1. PROXY=direct: no proxy, not even the system's.
  2. PROXY, with NO_PROXY for the hosts that bypass it.
  3. The system proxy: on Windows the WinHTTP proxy (netsh winhttp) or the machine-wide Internet settings, on macOS the proxies set in System Settings > Network. NO_PROXY applies to it too. Linux has no system proxy setting.
  4. Direct.

A system proxy that fails before any request has gone through it is skipped for the rest of the run, with one warning; an explicit PROXY is never bypassed. Credentials go in the URL (http://user:password@proxy.corp:3128, Basic authentication). Not supported: PAC files and WPAD, and NTLM or Kerberos proxy authentication.

TLS inspection (custom CA)

If a proxy inspects TLS, set CA_CERT to a PEM file holding its CA certificate. The certificates are added to the system trust store, not used instead of it.

On 0.16.0 and earlier

The agent reads these from the env file under their older names, and only TOKEN can be given to the installer. Proxy variables and CA_CERT_PATH exported for register (sudo -E) are stored in the file too. After editing the file, restart the service:

HTTPS_PROXY=http://proxy.corp.com:8080
NO_PROXY=localhost,127.0.0.1
CA_CERT_PATH=/etc/ssl/certs/corp-ca.pem
LOG_LEVEL=debug
# Linux
sudo systemctl restart licenseware-collector
# macOS
sudo launchctl kickstart -k system/io.licenseware.licenseware-collector
# Windows (Administrator PowerShell)
Restart-Service licenseware-collector

The Windows and macOS services of 0.16.0 and earlier ignore CA_CERT_PATH: add the CA certificate to the operating system trust store instead (Windows: Trusted Root Certification Authorities of the local computer; macOS: the System keychain), which the collector always trusts.

3No registration state: not enrolled, an enrolment still pending, or a golden image before its first start
4Service not installed
5Only with --require-healthy: registered, but not healthy

Checked in the order 1, 4, 3, 2, 0. A stopped but registered service still exits 0. On Windows, a caller that cannot query the service (a standard user in a scheduled task) is judged by the state file alone. Exit codes 0–4 exist from 0.16.0, 5 from 0.17.0.

Updates

From 0.17.0 agents update themselves on every OS from cdn.licenseware-collector.com: signed releases, checked every 24 hours, and rolled back automatically when the new version does not start and reach Licenseware. AUTOUPDATE=0 stops it on a machine (Settings). On 0.16.0 and earlier, Windows and Linux agents update from GitHub every 24 hours, and macOS agents never update themselves.

  • Config Refresh: 30 mins
  • Catalog Check: 30 mins
  • Failed File Cleanup: 6 hours
On 0.16.0 and earlier

Uninstall Guide

⚠️ Requires elevated privileges (sudo on Linux/macOS, Administrator on Windows)

Linux

  1. Debian / Ubuntu
    sudo apt remove licenseware-collector
  2. RHEL / Fedora / SUSE
    sudo dnf remove licenseware-collector

Removing the package stops the service and runs the uninstaller for you. Do not call licenseware-collector uninstall directly on a package-managed host — it refuses and points you back at the package manager.

macOS

Download uninstall.command from the Downloads section and double-click it, or run it from Terminal: 

sudo LICENSEWARE_UNINSTALL_FROM_PACKAGE=1 \
  /usr/local/libexec/licenseware-collector/licenseware-collector uninstall --force
sudo rm -rf /usr/local/licenseware-collector
sudo pkgutil --forget io.licenseware.collector

Windows (Administrator PowerShell)

  1. Uninstall the package 
    msiexec /x LicensewareCollector.msi
  2. Or remove it from the UI:
    Settings > Apps > Installed apps
Uninstalling stops the service, removes it, and deletes the collector's runtime files and enrollment token from the machine. The package removals above (msiexec /x, apt remove / dnf remove and uninstall.command) run with fixed arguments and take no extra options: --preserve-state and --remove-osquery are options of the licenseware-collector uninstall command, not of msiexec.
From 0.17.0, uninstall (Windows: LicensewareCollector.exe uninstall) removes a package install through its package manager on every OS, so the refusal above applies only to 0.16.0 and earlier. See Day-2 operations, and for Intune and SCCM the uninstall command.

Data Collection Specification

This section lists every query the Collector runs, the operating systems it runs on, how often, the exact fields collected and why. It is the same specification published as Schedule 3 of the Licenseware Data Processing Addendum, which governs all data transmitted by the Collector. Nothing outside this list is collected.

The Collector runs two fixed catalogues. Catalogue definitions are fetched from the platform every 30 minutes and results are sent over TLS to the regional instance encoded in your enrolment token. Field names are the column names of the underlying osquery tables.

The query, field and purpose tables below are published in English. The English text is the operative version regardless of the language selected for this site.

What the Collector does not collect

  • File contents, documents, email or messaging content
  • Browser history, keystrokes, screen content or network traffic
  • Process command-line arguments or program argument strings (removed from all queries on 3 September 2026)
  • Anything outside the queries listed below. Where a query is restricted to named directories or registry keys, the restriction is shown in the field list.

Personal data

Several queries return personal data about the people who use the system: local usernames and home paths, logged-in sessions, per-user program execution history and process ownership. These are flagged in the right-hand column. If you deploy the Collector you are the controller of that data and should cover it in employee privacy notices and, where required, works council consultation before rollout. Our DPIA Support Document (Processor Information) walks through each item.

Logs & Troubleshooting

The collector writes its logs to standard error; the Windows service writes them to the Windows Event Log instead. How you access them depends on the operating system and service manager.

Linux

On systemd-based systems, logs are captured by the journal automatically.

Follow logs in real time:
journalctl -u licenseware-collector -f
View logs from the last hour:
journalctl -u licenseware-collector --since "1 hour ago"

macOS

The launchd service writes both stdout and stderr to a single log file.

Follow logs in real time:
tail -f /var/log/licenseware-collector.log
View full log file:
cat /var/log/licenseware-collector.log
From 0.17.0 the file is rotated at 10 MB and 7 compressed copies are kept. Package install failures (exit codes 20–23) are in /var/log/install.log: 
grep -i licenseware /var/log/install.log

Windows

The Windows service writes the collector's log to the Windows Event Log under the licenseware-collector provider; it writes no log file. Run these in an Administrator PowerShell.

The collector's own log (stderr is not captured for services): 
Get-WinEvent -ProviderName "licenseware-collector" -MaxEvents 50
The installer's log. It records what the setup helper and register printed, including why an enrolment failed, and it survives the rollback that removes everything else. The enrolment token is never written to it: 
Get-Content C:\ProgramData\Licenseware\setup.log
Windows Installer's own log, for an install that fails or is refused before the setup helper runs. Re-run the MSI with verbose logging; the token is a hidden property and is never written to this log: 
msiexec /i LicensewareCollector.msi TOKEN=<enrolment-token> /l*v install.log
Get-Content install.log -Tail 200
For more detail, set LOG_LEVEL=debug (Settings) and set it back to info when done. From 0.17.0, diagnose collects these logs into a redacted support bundle (Day-2 operations).
